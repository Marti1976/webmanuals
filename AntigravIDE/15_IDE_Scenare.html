Případ 1: Receptář (Tvůj Projekt)

Situace: Máš React receptář. Chceš přidat novou feature: "Ceník receptářů" — tabulka se jmény receptů a cenami. Strukturovaně to dělat 3 agenty: Designer, Implementer, Tester.

Agenti & Role

  • Agent Designer: Navrhuje UI — layout, barvy, responsive design
  • Agent Implementer: Píše React kód na základě designu
  • Agent Tester: Píše testy, kontroluje že vše funguje

Workflow — Krok za Krokem

Krok 1: Designer pracuje (Den 1, ráno)

Prompt: "Navrhni nový component PriceTable pro receptář. Bude to tabulka se 3 sloupci: nazev (left), kategorie (center), cena (right). Design by měl být modern, responsive (mobile friendly), v tónu Tailwind dark theme. Vygeneruj HTML + CSS preview a JSDoc interface."

Co Designer udělá:

  • Navrhne layout (CSS grid / flexbox)
  • Vypadá z Tailwind palette
  • Generuje Artifact s `index.html` + `styles.css`
  • Píše JSDoc interface:
    /**
     * @param {Array} recipes - List of recipes
     * @param {string} recipes[].name - Recipe name
     * @param {string} recipes[].category - Category
     * @param {number} recipes[].price - Price in CZK
     */
    function PriceTable({ recipes }) { ... }

Výstup Designer: Artifact s designem, TypeScript types soubor

Krok 2: Implementer dostane input (Den 1, v poledne)

Prompt: "Tady je design od Designer agenta (viz Artifact). Teď to implementuj jako React komponentu. Soubor: src/components/PriceTable.tsx. Musíš respektovat interface (types Designer vymyslel). Props jsou: recipes (Array). Komponenta bude sortovatelná — klik na header = sort."

Co Implementer udělá:

  • Vytvoří `src/components/PriceTable.tsx`
  • Implementuje React logiku (useState pro sort state)
  • Používá Tailwind třídy ze Designerova návrhu
  • Respektuje TypeScript types
  • Testuje lokálně: `npm run dev`
  • Commituje: `git commit -m "feat: PriceTable component"`

Výstup Implementer: Nový React soubor, git commit

Krok 3: Tester kontroluje (Den 1, odpoledne)

Prompt: "Tady je nový PriceTable component od Implementera. Napiš unit testy. Test soubor: src/components/__tests__/PriceTable.test.tsx. Testuj: 1) vyrenderuje se správně, 2) sorting funguje, 3) props se aplikují správně. Framework: Vitest + React Testing Library."

Co Tester udělá:

  • Napíše test soubor
  • Spustí `npm run test`
  • Kontroluje že všechny testy projdou
  • Reportuje: "Všechno OK" nebo "Chyba v sort logice"

Výstup Tester: Test soubor, report pokrytí

Handoff Data — Co si Předávají

Designer → Implementer:
• Artifact (HTML/CSS preview)
• TypeScript interface (@types)
• Color palette (konkrétní Tailwind třídy)

Implementer → Tester:
• Git commit se kódem
• JSDoc comments
• Specifikace testů (co testovat)

Tester → Všichni:
• Test results (PASS/FAIL)
• Coverage report

Potenciální Konflikty & Řešení

Konflikt 1: Designer udělal design v jedné barvě, Implementer ji změní.

Řešení: RULE: "Agent Implementer: CSS barvy a styling jsou READ-ONLY z Design interface. Neměníš je bez Designer schválení."

Konflikt 2: Implementer neimplementuje všechny features z designu (např. animation).

Řešení: Jasný prompt: "Implementuj PŘESNĚ toto. Pokud nelze → řekni proč a počkej na guidance."

Výsledek — Co se stane

  • ✅ PriceTable komponenta je implementovaná
  • ✅ Design je respektován
  • ✅ Kód je testovaný
  • ✅ Git history je čistá (tři jasné commity)
  • ✅ Čas: ~2-3 hodiny (místo 1 agenta: 4-5 hodin)

Metriky pro Tento Scénář

Čas: Designer 45min, Implementer 60min, Tester 30min = 2h15min

Kvalita: 100% design compatibility, 90% test coverage, 0 bugs post-release

API quota: ~2000 tokens (průměr na agenta)

Případ 2: Návody & Tutoriály (Paralelní Systém)

Situace: Chceš napsat kompletní tutoriál "Jak psát agenty v Antigravity IDE" (právě to co čteš!). To je 4 věci které se MOHOU dělat paralelně:

  • Agent STRUKTURA: Vymyslí outline (co všechno by mělo být)
  • Agent OBSAH: Píše samotný text
  • Agent KÓDOVNÍK: Píše příklady kódu
  • Agent EDITOR: Kontroluje grammar, konzistenci, flow

Rozdíl od Receptáře

Receptář: SEKVENČNÍ — Designer → Implementer → Tester. Jeden čeká na druhého.

Návody: PARALELNÍ — všechny 4 agenti pracují ZÁROVEŇ. Pak se výstupy skombinují.

Workflow

Fáze 1: Struktura (Start, všichni)

Agent STRUKTURA prompt: "Vytvoř outline pro tutoriál 'Agenty v Antigravity IDE'. Měl by pokrývat: co jsou agenti, jak je vytvořit, orchestrace, příklady. Vrať seznam sekcí s počtem slov na sekcí."

Výstup: Markdown outline

Fáze 2A: Obsah (Paralelně)

Agent OBSAH prompt: "Tady je outline. Napiš sekci 1 (úvod) a sekci 2 (vytvoření agenta). Stylem jednoduše, bez komplexního žargonu. ~3000 slov."

Fáze 2B: Kód (Paralelně)

Agent KÓDOVNÍK prompt: "Pro každou sekcí v outline, vytvoř pracovní příklad kódu. Soubory: example-1.ts, example-2.ts atd. Všechny příklady by měly být spustitelné."

Fáze 2C: Edit (Čeká na obsah, pak kontroluje)

Agent EDITOR prompt: "Tady je text od OBSAH agenta. Kontroluj: 1) Gramatiku, 2) Konzistenci stylu, 3) Je to srozumitelné? Vrať annotovanou verzi se 'change suggestions'."

Handoff Data

STRUKTURA → všem:
Outline (guide co dělat)

OBSAH + KÓDOVNÍK → paralelně:
Pracují nezávisle

OBSAH + KÓD → EDITOR:
Editor dostane finální texty a kód
Editor output → MASTER soubor

Výhoda Paralely

Sériově (1 agent): Strukturu → obsah → kód → edit = 12 hodin

Paralelně (4 agenti): Struktura (1h) + paralelní (3h pro zbylé) = 4 hodiny

Úspora: 8 hodin! (3x rychleji)

Metriky

Čas: 4 hodiny (místo 12)

Kvalita: Stejná (editor všechno kontroluje)

API quota: ~4000 tokens (všichni zároveň)

Případ 3: E-shop (Komplexní Workflow — 6 Agentů)

Situace: Staví se malý e-shop. To je velkej projekt: frontend, backend, databáze, payment, logika. 6 agentů pracuje na různých částech.

Agenti & Role

  • ARCHITECT: Navrhuje databázi, API struktura
  • FRONTEND: React UI (produkty, košík, checkout)
  • BACKEND: Express API (endpoints, business logika)
  • INTEGRATOR: Payment gateway (Stripe), email notifikace
  • TESTER: Unit + integration testy
  • REVIEWER: Code review všech ostatních

Workflow — Seriózní Závislosti

ARCHITECT (Databáze)
    ↓
BACKEND (API endpointy) ← FRONTEND (React)
    ↓                    ↙
INTEGRATOR (Payments)
    ↓
TESTER (Všechno)
    ↓
REVIEWER (Final check)

Detailní Workflow

Den 1: Architektura

Agent ARCHITECT: "Navrhni databázi pro e-shop. Tabulky: Users, Products, Orders, OrderItems. Všechny relace (foreign keys). Vygeneruj SQL schema a ER diagram."

Výstup: schema.sql, dokumentace

Den 1-2: Frontend & Backend (Paralelně)

Agent FRONTEND: "Máš DB schema od Architectu. Vytvoř React stránky: 1) Product list, 2) Product detail, 3) Shopping cart. Neimplementuj payment ještě. API endpoint mockuješ JSON."

Agent BACKEND: "Máš DB schema. Vytvoř Express API: GET /products, GET /products/:id, POST /orders, GET /orders/:id. Databázi připoj."

Den 2-3: Integration

Agent INTEGRATOR: "Frontend a Backend jsou hotové. Teď: 1) Stripe integration pro payment, 2) Email notifikace (SendGrid) když je objednávka placena."

Den 3: Testing

Agent TESTER: "Všechny komponenty jsou hotové. Napiš testy: 1) Frontend unit tests (React components), 2) Backend API tests (endpoints vracejí správná data), 3) Integration test (Frontend → Backend → Payment flow)."

Den 3: Review & Release

Agent REVIEWER: "Code review všech PRů. Kontrola: 1) Security (SQL injection?, auth?), 2) Performance, 3) Code style, 4) Test coverage."

Závislosti & Paralelizace

Co se NE-dá dělat paralelně:

  • Backend musí čekat na DB schema (závislost)
  • Integration musí čekat na Backend & Frontend (závislost)
  • Tester musí čekat na vše (závislost)

Co se dá paralelně:

  • Frontend & Backend — pracují nezávisle, pak se integrují
  • Během Backend vývoje — Frontend už připravuje UI (mockuje API)

Interface Definition (Smlouva)

Aby se Frontend a Backend nepletli, existuje api.types.ts:

// BACKEND vrací toto:
interface Product {
 id: string;
 name: string;
 price: number;
 image: string;
}

// FRONTEND to očekává:
const [products, setProducts] = useState<Product[]>([]);

Komunikace Mezi Agenty

ARCHITECT → BACKEND: "Tady je schema.sql — to je tvůj input."

BACKEND → FRONTEND: "API dokumentace: GET /products vrací Product[]."

FRONTEND & BACKEND → INTEGRATOR: "Tady je kód — sem integruj payment."

Všichni → TESTER: "Tady jsou naše PRů — testuj prosím."

Možné Konflikty

Konflikt 1: Frontend čeká na Backend API, ale Backend není hotový.

Řešení: Frontend používá mock server (json-server / msw) — pracuje na mockových datech. Až je Backend hotový, změní jen mock server.

Konflikt 2: Backend změní API struktura (product.name → product.title).

Řešení: Interface je SOURCE OF TRUTH. Backend ji nemůže změnit bez Frontend schválení. RULE: "Agent Backend: API interface je read-only bez Frontend schválení."

Výsledek & Metriky

Čas: 3 dny (Den 1: Architektura, Den 2: Frontend+Backend paralelně, Den 3: Integration+Testing+Review)

Kvalita: Všechno je code-reviewed, 85%+ test coverage, 0 production bugs v první týdnu

API quota: ~8000 tokens (6 agentů, různé doby)

Paralelizace efekt: Bez koordinace by to trvalo 8 dní (sériově). S koordinací 3 dny = 2.6x zrychlení.

Benchmark Setup — Jak Měřit Efektivnost

Jak víš jestli je tvůj multi-agent systém efektivní? Tady je jak to měřit.

Metriky

1. Čas (Time to Completion)

Co měřit: Kolik trvalo než je task hotový.

1 agent: 4 hodiny

3 agenti sekvenčně: 4.5 hodiny (overhead)

3 agenti optimálně: 2.5 hodiny (paralelizace)

2. Cost (API Usage)

Co měřit: Kolik tokenů spotřeboval API.

1 agent (4h): 4000 tokens
3 agenti (2.5h): 3500 tokens
Úspora: -12.5% (paralelizace je efektivnější!)

3. Quality (Metrics)

Co měřit: Počet bugů, test coverage, review comments.

1 agent:
- Bugs: 3
- Test coverage: 70%
- Review comments: 8

3 agenti (s Reviewerem):
- Bugs: 1
- Test coverage: 90%
- Review comments: 2 (reviewer už zkontroluje)

Výsledek: Kvalita je lepší!

4. Consistency (Reproducibility)

Co měřit: Vždy stejný výstup? Jsou výsledky konzistentní?

Spusť stejný task 3x — dostaneš stejný výstup? Pokud ne, je systém nestabilní.

Jak Měřit — Prakticky

Setup

  1. Máš konkrétní task (např. "Přidej filtr na cenu")
  2. Spustíš ho s 1 agentem — měříš čas, cost, quality
  3. Spustíš ho s 3 agenty — měříš opět
  4. Porovnáš výsledky

Příklad: Benchmark PriceTable

1 Agent (GENERALIST):
Time: 2 hours
Cost: 2500 tokens
Test coverage: 65%
Bugs found later: 2

3 Agenti (SPECIALIST):
Time: 1.5 hours
Cost: 2000 tokens
Test coverage: 92%
Bugs found later: 0

Winner: 3 Agenti ✅
- 25% rychleji
- 20% levnější
- Vyšší kvalita

Kdy Jsou Více Agenti Zbytečný

Pokud task je velmi jednoduchý: "Oprav chybu na řádku 5" → 1 agent je ideální. Overhead multi-agent systému ho zpomalí.

Pokud máš málo API kreditu: Multi-agent systém spotřebuje víc (ačkoliv efektivněji). Pokud máš limit — jednoduší 1 agent.

Pokud je task lineární bez paralelizace: Designer → Implementer → Tester (vždy ten pořadí). Paralelizace není možná. Overhead bez zisku.

Recommendations

Používej 1 agenta když: Task je jednoduchý, lineární, málo API kreditu

Používej 3-4 agenty když: Komplexní task, paralelní streamy, kvalita je kritická

Používej 6+ agentů když: Velmi velký projekt, vysoké nároky na kvalitu, máš API kredit

// sekce 05

Srovnání — Kdy Který Přístup

Receptář (Tvůj projekt): 3 agenti, sekvenční, fokus na kvalitu

Návody: 4 agenti, paralelní, rychlost & kvalita

E-shop: 6 agentů, komplexní DAG, vysoká kvalita & bezpečnost

Jaký model bys měl zvolit?

👉 Začni s 1 agentem — nauč se základy

👉 Pak 2-3 agenti — začíná se vyplácet

👉 6+ agentů — až když máš zkušenost a komplexní projekt
