Jeden vs Více agentů

Kdy jeden agent stačí

Jednoduchý projekt, lineární tok: Máš řetězec kroků kde každý krok logicky následuje. Například: "Přidej feature" → agent to implementuje. Nebo: "Napiš test" → agent to dělá. Jeden agent s jasným fokusem je nejjednodušší a nejrychlejší.

Příklady: Editace jednoho souboru, drobné opravy, jednorázové úkoly. Tvůj receptář v počátcích — když jsi jen přidával recepty a editoval UI.

Kdy potřebuješ více agentů

Komplexní projekt s paralelními streamy: Když máš věci které se mohou dělat nezávisle. Například: Frontend design se dělá ZÁROVEŇ s backend logikou, zatímco testy se píší paralelně. Jeden agent by dělal všechno sériově — bylo by to pomalé.

Specializované role: Agent na testy vidí kód jinak než agent na design. Každý má specifický mindset a constraints. Designer řeší CSS, architekt řeší databázi — jejich stavy jsou jiné.

Kontrola kvality: Když máš REVIEWER agenta, ten je čistě na code review a nic jiného nedělá. Není "zašumění" - je zaměřený.

ℹ️
Heuristika: Více agentů když máš 3+ nezávislých streamů

Pokud máš Feature A, Feature B a Testy — to jsou 3 věci. Mohou běžet paralelně? Pokud ano → více agentů. Pokud ne (testy závisí na Feature A) → sekvence je OK.

// sekce 02

Různé role agentů — 10 TOP typů

Tady je orientace co všechno může být agent. Není to seznam "měl by sem mít tyto 10" — je to "z těchto typů si vezmi co potřebuješ".

1. ANALYZER (Čtenář & Konzultant)

Role: Čte kód/dokumentaci a radí co s ním. Neimplementuje, jen analyzuje. "Jaká je struktura tohoto souboru?" → vrací detailní analýzu. Ideální pro code review, architekturní rozhodnutí, identifikaci problémů.

2. IMPLEMENTER (Kodér)

Role: Píše kód. Frontend, backend, cokoliv. Nejčastější role. "Přidej tuto funkci" → implementuje. Pracuje s kompilátorem, rozumí TypeScript/JavaScript, spouští build.

3. TESTER (Tester)

Role: Píše testy. Unit testy, integration testy. Zná testing frameworky. Kontroluje že kód FUNGUJE. Má přístup k test runnerům.

4. DESIGNER (UI/UX Developer)

Role: CSS, designové rozhodnutí. Pracuje s Tailwind, zná principy designu. Nemá v pověření psát business logiku — fokus jen na vzhled.

5. ARCHITECT (Stavitel Struktury)

Role: Návrh databází, API structure, project layout. "Jak bychom měli organizovat data?" → vymyslí schéma. Vysokoúrovňová rozhodnutí.

6. REVIEWER (Code Review Expert)

Role: Jen review. Čte co ostatní agenti napsali. Kontroluje style, security, performance. Gatekeeping role — povoluje nebo zamítá PR.

7. OPTIMIZER (Rychlostář)

Role: Perf optimalizace. "Tahle funkce je pomalá" → zkrátí ji. Zná algoritmy, caching, lazy loading. Fokus na metriky.

8. DOCUMENTER (Dokumentaři)

Role: Píše docs, README, JSDoc comments. Komunikátor. Umí vysvětlit věci jednoduše.

9. DEBUGGER (Lovec Bugů)

Role: Když selže build nebo runtime error — tento agent to fixuje. Čte error messages, zná debug tooling. Expert na "co se stalo".

10. GENERALIST (Univerzální Hráč)

Role: Kombinuje víc věcí. Není jen developer ani jen designer — je multi-tool. Ideální pro malé projekty. Může nahradit 3-4 specializované agenty, ale s menší přesností.

✓
Praktické pravidlo: Máš-li čas a rozpočet → více specializovaných

Máš-li málo času → jeden GENERALIST. Náš receptář? Designer + Implementer + Tester (3 agenti) je sweet spot.

// sekce 03

Jak spolu agenti pracují

Multi-agent systém není chaos. Je to orchestrovaný tanec. Tady je jak to funguje:

Fáze 1: Definice Task & Role

TY definuješ: "Agent Designer navrhne nový interface pro feature X. Pak Agent Implementer jej postaví. Pak Agent Tester jej testuje." Každý ví co má dělat a co ČEKÁ od ostatních.

Fáze 2: Designer pracuje

Agent Designer dostane: "Navrhni strukturu UI pro ceník receptáře. Výstup: Figma soubor / wireframe / popis layoutu." Pracuje, generuje Artifacts (designové návrhy).

Fáze 3: Handoff — Implementer dostane input

Agent Implementer vidí co Designer udělal. Dostane output: "Tady je wireframe, tady jsou barvy, tady jsou komponenty." Implementer říká: "OK, teď kóduji" a píše React komponenty podle návrhu.

Fáze 4: Implementer hotov

Výstup: Kód (Pull Request, nové soubory). Agent Tester vidí kód.

Fáze 5: Tester kontroluje

Agent Tester: "OK vidím React kód. Teď napíšu testy." Píše unit testy pro komponenty. Spouští npm test. Všechno green? Hotovo. Failure? Report agentovi Implementer co fixnout.

Výměna dat — jak si předávají věci

Agenti si předávají věci přes:

  • Git commits: Implementer commituje kód, Tester vidí v repo
  • Comments v kódu: "Agent Designer sem napíšu komentář co to má být"
  • Interface soubory: types.ts — "tady je kontrakt co očekávám"
  • Artifacts v Antigravity IDE: Agenti si vidí chystané změny v Approval panelu
// sekce 04

Komunikace mezi agenty

Agenti nekomunikují "mluvením" (nejsou v chatu spolu). Komunikují přes:

1. Kód & Artifacts

Agent Designer generuje Design Artifact. Agent Implementer ho vidí v panelu. To je komunikace — vizuální, jasná.

2. Git History

Commit message: "Designer: Added primary colors palette". Implementer vidí git log a ví co se změnilo a proč.

3. TypeScript Interfaces (Smlouva)

V souboru types.ts:

interface RecipeCard {
 id: string;
 name: string;
 image: string; // Agent Designer: URL to image
}

To je smlouva: "Implementer — ty MUSÍŠ poskytnout tyto fieldy. Designer — ty MUSÍŠ respektovat tuto strukturu."

4. RULES & Comments

V .antigravity-rules nebo v comments: "Agent Implementer: Neměň CSS, to je role Designera" → explicitní komunikace.

5. Approval & Feedback

Když Implementer commituje — ty (orchestrující) můžeš napsat: "Agent Tester: tohle je špatně, fixni" → Tester vidí a opravuje.

⚠️
Agenti si NEMŮŽOU psát zprávy přímo

Nedělají to tak: Agent1 píše agentovi Agent2 v chatu. To by bylo chaos. Místo toho: Předávají si věci přes kód, commits, artifacts.

// sekce 05

Orchestrace — Kdo řídí

TY jsi orchestrátor. Ty říkáš: "Teď Designer. Pak Implementer. Pak Tester." Ty spravuješ workflow.

Antigravity IDE ti v tom pomáhá. Manager View je právě na tohle — vidíš všechny agenty, jejich stav, timeline.

Možnosti orchestrace

Sériová (sekvenční)

Designer → hotov → Implementer → hotov → Tester. Jeden po druhém. Pomalé ale jasné.

Paralelní

Designer + Implementer běží zároveň (pracují na různých částech). Tester až oba skončí. Rychlejší.

Hybrid

Designer končí feature A → Implementer začíná A. Zároveň Designer začíná feature B. Efektivní.

// sekce 06

Typické problémy & Jak se vyhnout

❌ Problém 1: Agenti si konfliktují

Designer říká "Barva je modrá", Implementer to změní na červenou. Konflikt!

Řešení: Jasné RULES. "Agent Implementer: CSS barvy jsou ONLY Designerova rozhodnutí. Ty je implementuješ, nemění je."

❌ Problém 2: Agenti nevědí co dělat

Dáš Implementerovi kód bez jasné specifikace. Neví co se očekává.

Řešení: Interface definice. TypeScript .d.ts soubor co říká "tady je kontrakt".

❌ Problém 3: Čekání a deadlock

Implementer čeká na Designera, Designera blokuje něco jiného. Nic se nedělá.

Řešení: Paralelizace. Pokud Implementer může pracovat na Feature A zatímco Designer dělá Feature B — pověz mu to.

❌ Problém 4: Nerealizovatelné očekávání

"Agent Tester: pokryj 100% kódu testy" — ale někdy je to nereálné.

Řešení: Realistické cíle. "80% pokrytí" je lepší.

✓
Součet všech problémů: Nedostatečná komunikace

Jasné role + jasné interface + jasné RULES = 90% problémů vyřešeno.
