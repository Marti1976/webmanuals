Základy Orchestrace — Kdo Řídí Tanec

Co je orchestrace? Orchestrace je řízení. TY jsi dirigent. Agenti jsou hudebníci. Dirigent říká: "Teď violiny (Designer). Pak klarinet (Implementer). Pak bubny (Tester)." Bez dirigenta by to byl chaos.

Principy Orchestrace

Princip 1: TY řídíš, Agenti se řídí

Jak to funguje: Ty určíš workflow. "Designer → Implementer → Tester". Každý agent vidí svou roli v řetězci. Agenti se NEDOMLUVUJÍ navzájem — oni se podřizují tvému plánu.

Příklad (špatně): Dáš agentům volnost. "Dělej co chceš, domluv se s ostatními." Výsledek: Chaos. Agenti dělají věci v špatném pořadí.

Příklad (správně): Ty řekneš: "1) Designer navrhne UI. 2) Implementer implementuje. 3) Tester testuje." Každý ví co dělá a kdy.

Princip 2: Lineární vs Paralelní Tok

Lineární: Agent A → A skončí → Agent B → B skončí → Agent C. Postupně za sebou.

Paralelní: Agent A a Agent B běží ZÁROVEŇ. Když oba skončí → Agent C.

Kdy jaký? Lineární: Pokud B závisí na A (Implementer čeká na Designer). Paralelní: Pokud si nekonfliktují (Frontend & Backend jsou nezávislí).

Princip 3: Data Flow

Co to znamená: Data tekou mezi agenty. Designer → Interface. Implementer dostane interface a implementuje. Tester dostane kód a testuje. Data jdou jedním směrem (nebo cyklicky když je bug).

VÝSTUP designeru → INPUT implementera
(interface) (interface + spec)

VÝSTUP implementera → INPUT testera
(kód) (kód ke testování)

FAILURE testera → INPUT implementera
(bug report) (co fixnout)

Orchestrace v Antigravity IDE — Jak To Dělat Prakticky

Kde to orchestruj? V Antigravity IDE Manager View. Vidíš všechny agenty, jejich stav, timeline.

Postup:

  1. Otevřeš Manager View
  2. Vidíš agenty (DESIGNER, IMPLEMENTER, TESTER)
  3. Pravý panel: Můžeš nastavit priority, paralelizaci
  4. Spustíš: "1) DESIGNER. Pak 2) IMPLEMENTER. Pak 3) TESTER."
  5. Sleduj progress — vidíš co dělají, kdy skončili

Kontrola: Když vidíš že Agent A skončil, můžeš spustit Agenta B. Nebo to nastavíš aby se spustilo automaticky.

// sekce 02

Komunikační Kanály — Jak Si Agenti Předávají Věci

Zásadní pochopení: Agenti se NEMLUVUJÍ. Neposílají si zprávy. Komunikují PŘES KÓD. Toto je kritické.

5 Hlavních Kanálů

1. Git Commits (Nejjednodušší)

Co to je: Když agent commituje kód, všichni vidí změnu.

Výhoda: Je to permanentní, traceable, má historii

Jak: Implementer writes code, commits: `git commit -m "feat: PriceTable component"`

Tester vidí: V `git log` vidí co se změnilo, proč

DESIGNER commituje:
git commit -m "design: PriceTable wireframe"

IMPLEMENTER vidí v git log a commituje:
git commit -m "feat: PriceTable React component"

TESTER vidí v git diff a testuje:
git show HEAD (vidí co se změnilo)
Píše testy a commituje:
git commit -m "test: PriceTable unit tests"

2. Artifacts (Antigravity IDE Feature)

Co to je: Agent generuje Artifact (soubor, preview, design). Ostatní to vidí.

Výhoda: Vizuální, jasné, live preview

Jak: Designer generuje HTML preview v Artifact. Implementer ho vidí.

DESIGNER generuje Artifact:
[Shows HTML preview of PriceTable design]

IMPLEMENTER vidí v Approval panel:
"Artifact: HTML preview"
[Klikne na něj a vidí design]

IMPLEMENTER pak implementuje React:
[Generuje svůj Artifact se React komponentou]

3. TypeScript Interface Files (.d.ts)

Co to je: Soubory s typovými definicemi. "Tady je kontrakt."

Výhoda: Přesné, nully ambiguity, machine-readable

Jak: Designer píše interface, všichni si ho odsud vezmou

File: src/types/PriceTable.d.ts

export interface Recipe {
id: string
name: string
price: number
category: 'soup' | 'main' | 'dessert'
}

export interface PriceTableProps {
recipes: Recipe[]
onSort?: (field: keyof Recipe) => void
}

IMPLEMENTER čte toto a ví:
"OK, component dostane recipes array.
Každý recipe má id, name, price, category.
Optional onSort callback."

TESTER čte toto a ví:
"Testuju s těmito types.
Když předám špatný type → fail test."

4. Comments & Documentation

Co to je: Code comments, JSDoc, README notes

Výhoda: Vysvětluje PROČ, ne jen CO

Jak: Agent napíše komentář co vysvětluje rozhodnutí

/**
* Designer Agent Note:
* I chose flexbox here (not grid) because
* we need equal height columns on mobile.
* Grid has limitations on older phones.
* — DESIGNER Agent
*/
.priceTable {
@apply flex flex-col gap-4;
}

5. Approval & Feedback Panels

Co to je: V Antigravity IDE vidíš approval panel. Tam se hlasuje / dává feedback.

Výhoda: Synchronní komunikace (live feedback)

Jak: Implementer pushne PR → vidíš v approval panelu → můžeš komentovat → agent vidí a opravuje

IMPLEMENTER pushne kód
[Approval panel shows the code]

TY napíšeš komentář:
"Button color is wrong — should be blue"

IMPLEMENTER vidí feedback a opravuje:
"Changing button color to blue"

TY schvalíš:
[Approve] ✓

IMPLEMENTER vidí že je schváleno a commituje

Strategie: Který Kanál Kdy

Definitivní: Git commits + TypeScript interfaces (permanentní, machine-readable)

Vizuální: Artifacts (HTML previews, designs)

Vysvětlující: Comments (proč byly rozhodnutí)

Feedback: Approval panel (live discussion)

Pro tvůj receptář s 3 agenty: Používej všechny. Git commits primárně, Artifacts pro design, TypeScript interfaces pro kontrakty, Comments pro vysvětlení.

Interface Definice — Smlouva Mezi Agenty

Co to je? Interface je smlouva. "Implementer: Já (Designer) ti dávám TOTO. Ty MUSÍŠ RESPEKTOVAT. Nemůžeš to měnit."

Proč je to kritické? Bez interface by Implementer mohl změnit design (přidat svou barvu). Ale interface říká: "Barvy jsou READ-ONLY — Designer je nastavila."

Interface Hierarchie

Level 1: Component Props (Nejdůležitější)

Co: Jaké props dostane component?

// DESIGNER definuje:
export interface PriceTableProps {
recipes: Array<{
id: string
name: string
price: number
}>
sortBy?: 'name' | 'price'
onSort?: (field: string) => void
}

// IMPLEMENTER vidí a ví:
// "Props musím PŘESNĚ takhle implementovat.
// Nic víc, nic míň."

// TESTER vidí a ví:
// "Testuju s těmito props types."

Level 2: Data Models (Struktury)

Co: Jaké jsou data structures? (Database, API responses)

// ARCHITECT definuje:
export interface Recipe {
id: string // UUID
name: string // max 100 chars
description?: string
price: number // in CZK
category: 'soup' | 'main' | 'dessert'
createdAt: Date
updatedAt: Date
}

// BACKEND API vrací:
GET /api/recipes → Recipe[]

// FRONTEND čeká tyto fieldy:
const recipes: Recipe[] = await fetch(...)

// TESTER testuje s těmito types

Level 3: API Contracts (Komunikace Backend-Frontend)

Co: Jaké jsou API endpoints? Jaké data berou/vrací?

// ARCHITECT definuje:

GET /api/recipes
Response: { data: Recipe[], total: number }

POST /api/recipes
Body: Omit
Response: { data: Recipe }

GET /api/recipes/:id
Response: { data: Recipe }

// BACKEND implementuje PŘESNĚ takto
// FRONTEND volá PŘESNĚ s těmito parametry
// TESTER testuje PŘESNĚ toto

Jak Zajistit Compliance (Dodržování)

Problém: Interface je napsaný, ale Agent ho ignoruje.

Řešení 1: TypeScript Strict Mode

// tsconfig.json
{
"compilerOptions": {
"strict": true, // STRICT!
"exactOptionalPropertyTypes": true,
"noImplicitAny": true
}
}

// Pokud IMPLEMENTER napíše
const MyComponent = ({ recipes, unknown }) => {
// ^^^^^^^^^^ TypeScript FAIL!
// "unknown" není v PriceTableProps
}

// Build nefunguje. Agent musí fixnout.

Řešení 2: Explicit Rule v .antigravity-rules

RULE: Interface je READ-ONLY
RULE: DESIGNER definuje interface, IMPLEMENTER ji respektuje
RULE: Změna interface = potřeba schválení DESIGNERA
DENY: IMPLEMENTER měnit interface sám
DENY: BACKEND vrátit jiné fieldy než v API contract

Řešení 3: Runtime Validation

// IMPLEMENTER používá runtime validation
import { z } from 'zod'

const RecipeSchema = z.object({
id: z.string(),
name: z.string(),
price: z.number(),
category: z.enum(['soup', 'main', 'dessert'])
})

// API vrací data
const response = await fetch('/api/recipes')
const data = await response.json()

// Validuj!
const recipes = RecipeSchema.array().parse(data)
// Pokud data neodpovídají → runtime error
// BACKEND vidí error a fixne

Závislosti & Workflow DAG — Kdo Čeká Na Koho

Co je DAG? DAG = Directed Acyclic Graph. To je diagram který ukazuje: "Agent A → Agent B → Agent C" nebo "A → B i C paralelně → D".

Příklad 1: Receptář (Sekvenční)

┌─────────┐
│ DESIGNER│ Design UI
└────┬────┘
│ (outputs interface)
▼
┌──────────────┐
│ IMPLEMENTER │ Code it
└────┬─────────┘
│ (outputs kód)
▼
┌────────┐
│ TESTER │ Test it
└────────┘

Závislosti:
• IMPLEMENTER čeká na DESIGNER (vstup: interface)
• TESTER čeká na IMPLEMENTER (vstup: kód)

Čas: Lineární — všichni za sebou
Duration: 1h + 1h + 0.5h = 2.5 hodin

Příklad 2: Návody (Paralelní)

┌─────────────┐
│ STRUKTURA │ (outline)
└──────┬──────┘
│
┌───────────┼───────────┐
▼ ▼ ▼
┌───────┐ ┌────────┐ ┌────────┐
│OBSAH │ │KÓD │ │PŘÍKLADY│ (paralelně)
└───┬───┘ └───┬────┘ └───┬────┘
│ │ │
└──────────┼───────────┘
▼
┌────────┐
│ EDITOR │ (final check)
└────────┘

Závislosti:
• OBSAH, KÓD, PŘÍKLADY — nezávislí (paralelně)
• EDITOR čeká na všechny 3 (vstup: výstupy)

Čas: Paralelní
Duration: 1h (struktura) + 3h (paralelně) = 4h vs Sériově: 12h

Příklad 3: E-shop (Komplexní DAG)

┌──────────┐
│ ARCHITECT│ DB schema
└────┬─────┘
│
├──────┬──────────┐
│ │ │
▼ ▼ ▼
┌────┐ ┌────────┐ ┌────────┐
│BACK│ │FRONTEND│ │[wait] │
└─┬──┘ └────┬───┘ └────────┘
│ │
└────┬────┘
▼
┌──────────┐
│INTEGRATOR│ Payments
└────┬─────┘
│
▼
┌────────┐
│ TESTER │ All tests
└────┬───┘
│
▼
┌────────┐
│REVIEWER│ Final check
└────────┘

Závislosti:
• BACKEND čeká na ARCHITECT
• FRONTEND je téměř nezávislý (mock server)
• INTEGRATOR čeká na BACKEND & FRONTEND
• TESTER čeká na INTEGRATOR
• REVIEWER vidí všechno

Strategie paralelizace:
ARCHITECT (1h)
→ BACKEND (2h) + FRONTEND (2h) paralelně
→ INTEGRATOR (1h)
→ TESTER (1h)
→ REVIEWER (0.5h)
Total: 5.5h (místo 8h sériově)

Jak Definovat DAG Pro Tvůj Projekt

Postup:

  1. List všechny agenty které potřebuješ
  2. Definuj "co agent dostane" (input) a "co agent vydá" (output)
  3. Nakresli šipky — "agent A → agent B" znamená "A musí skončit před B"
  4. Hledej paralelizaci — pokud jsou agenti nezávislí, běží zároveň
  5. Spočítej čas — Max(paralelní) + Sum(sériové)

Pro receptář (TVŮJ PROJEKT):

Agenti: DESIGNER, IMPLEMENTER, TESTER

Definice:
DESIGNER:
Input: Feature spec ("Přidej ceník receptů")
Output: Interface + HTML preview

IMPLEMENTER:
Input: DESIGNER output
Output: React komponenta (kód)

TESTER:
Input: IMPLEMENTER output
Output: Test soubory + test report

DAG:
DESIGNER → IMPLEMENTER → TESTER
(sériově, není paralelizace)

Čas: ~2.5 hodin na featuru

Konflikt Resolution — Když Se Agenti Neshodnou

Kdy se to stane? IMPLEMENTER dostane design, ale myslí si že to je špatně. "Barva by měla být modrá, ne červená." Konflikt!

Typy Konfliktů

Typ 1: Design vs Implementation

Co: Implementer chce změnit design.

Příčina: Možná je design nerealistický (2s load time na mobilu) nebo technicky nemožný.

Řešení: RULE: "IMPLEMENTER: Nemůžeš měnit design sám. Pokud není možný → reportuj DESIGNEROVI. DESIGNER dělá rozhodnutí."

IMPLEMENTER čte design a vidí:
"Button animation — 0.2s transition + glow effect"

IMPLEMENTER myslí:
"To bude pomalé. Sníží performance na mobilu."

❌ ŠPATNĚ:
IMPLEMENTER odstraní animation (bez schválení)

✅ SPRÁVNĚ:
IMPLEMENTER napíše komentář:
"Designer: Animation 0.2s + glow = 60fps loss on mobile.
Suggestion: Reduce to 0.1s or remove glow.
What's your priority — animation or performance?"

DESIGNER vidí a rozhodne:
"OK, 0.1s je OK."

IMPLEMENTER pak to implementuje.

Typ 2: Implementace vs Testing

Co: Tester najde bug, ale Implementer nesouhlasí že je to bug.

Příčina: Různé chápání specifikace.

Řešení: RULE: "Pokud Tester říká že je to bug → je to bug. Dokud není fixnuto, nechoď dál."

TESTER testuje component:
test('button is disabled when loading', () => {
// Expected: button disabled
// Actual: button is clickable
expect(isDisabled).toBe(true) // FAIL
})

IMPLEMENTER vidí a řekne:
"To není bug. Uživatel musí být schopný
znovu kliknout na button."

❌ ŠPATNĚ:
IMPLEMENTER ignoruje test, pokračuje dál.

✅ SPRÁVNĚ:
IMPLEMENTER kouká na spec:
"Spec říká: Button DISABLED během loadingu."
"Uživatel se mýlil. Musím fixnout."

IMPLEMENTER commituje fix.

Typ 3: Data Model Conflict

Co: Frontend čeká `recipe.price`, Backend vrací `recipe.cost`.

Příčina: Interface nebyl jasný, agenti pracovali nezávisle.

Řešení: Tento konflikt se VŮBEC neměl stát. Solution: TypeScript Interface je SOURCE OF TRUTH.

❌ ŠPATNĚ (bez interface):
BACKEND (nezávisle) vrací:
{ id, name, cost }

FRONTEND (nezávisle) čeká:
{ id, name, price }

Runtime: Frontend vidí undefined price → bug

✅ SPRÁVNĚ (s interface):
Interface (ARCHITECT definuje):
interface Recipe { id, name, price }

BACKEND: "Musím vrátit `price`" (TypeScript error)
FRONTEND: "Čekám `price`" (TypeScript satisfied)

Konflikt se nestane — TypeScript to chytí.

Generální Strategie Konflikt Resolution

Princip 1: Jasný Ownership

Každá rozhodnutí má jednoho ownera. Design decisions = DESIGNER (final say). Implementation decisions = IMPLEMENTER (final say). Test coverage = TESTER (final say).

Princip 2: Interface Je Zákaz

Pokud je něco v interface/types → je TO ZÁKAZ. Neměnitelné. Pokud chceš to změnit → schválení owncera.

Princip 3: Escalation

Pokud se dva agenti neshodnou → escalate to YOU (orchestrátor). TY rozhodneš.

⚠️
Nejčastější chyba: Moc vágní specifikace

Bez jasné specifikace (interface, rules) se konflikty násobí. Čas na specifikaci se vrátí.

Best Practices & Anti-Patterns — Co Funguje, Co Ne

✅ BEST PRACTICES

1. Jasné Role & Ownership

Pravidlo: Každý agent má jasnou roli. "DESIGNER navrhuje, IMPLEMENTER kóduje, TESTER testuje." Žádná nejasnost.

Jak: Napíšeš role definition (viz Kapitola 13). Všichni ji čtou a podřizují se.

2. Interface First

Pravidlo: Předtím než agenti začnou → definuj interface. "Tady je kontrakt. Všichni se podřizují."

Jak: Vytvoříš TypeScript files s interfacemi. ARCHITECT to dělá.

Výhoda: 90% konfliktů se nikdy nestane. TypeScript to chytí compile-time.

3. Explicit Communication Rules

Pravidlo: Jak si agenti předávají věci? Git? Artifacts? Comments? Všichni to vědí.

Jak: V .antigravity-rules: "DESIGNER outputs: Artifact + interface. IMPLEMENTER consumes: Artifact + interface. TESTER consumes: code from git."

4. Review-Driven Approval

Pravidlo: Když agent skončí → vidíš to, můžeš schválit nebo poprosit o změnu.

Jak: V Antigravity IDE Manager View nastavíš Approval Mode = Review-Driven

Výhoda: Plná kontrola. Žádné surprise.

5. Atomic Commits

Pravidlo: Jeden agent = jeden commit. Není chaos. Git history je čistá.

Jak: RULE: "One task = one commit"

✅ DOBRÉ:
git commit -m "feat: PriceTable component"
git commit -m "test: PriceTable unit tests"
git commit -m "docs: PriceTable JSDoc"

❌ ŠPATNÉ:
git commit -m "did stuff"
(3 věci v jednom commit — historie je nepřehledná)

6. Constraint-Driven Design

Pravidlo: Agenti mají limity. "DESIGNER: dark theme only. IMPLEMENTER: TypeScript strict. TESTER: 80%+ coverage."

Jak: Rules a Constraints v system promptu + .antigravity-rules

Výhoda: Konzistentnost. Všichni vědí kam mohou, kam ne.

❌ ANTI-PATTERNS (Co Vyhnout)

Anti-Pattern 1: Vágní Specifikace

Problém: "Urci feature X" — co je feature X?

Výsledek: Všichni to chápou jinak. Chaos.

Jak se vyhnout: Napíšeš spec. "Feature X je: form s 3 inputy, validation, submit button, error handling. Interface je [types]. UI je [wireframe]."

Anti-Pattern 2: Agenti Si Posílají Zprávy (V Chatu)

Problém: IMPLEMENTER píše v chatu: "Designer, je to OK?". Chaos. Agenti nejsou chataři.

Výsledek: Chyby v komunikaci, delay.

Jak se vyhnout: Komunikace JE KÓD. Agenti si předávají věci přes Git, Artifacts, TypeScript files. Ne přes chat.

Anti-Pattern 3: Žádný Approval Gate

Problém: Agenti dělají co chtějí, bez tvého schválení.

Výsledek: Špatná kvalita. Bugs jdou do production.

Jak se vyhnout: Approval Mode = Review-Driven. VŠECHNO musí schválit TY (nebo REVIEWER agent).

Anti-Pattern 4: Příliš Mnoho Agentů

Problém: Máš 10 agentů. Orchestrace je nightmare.

Výsledek: Konflikty, overhead, komunikační chaos.

Jak se vyhnout: Start with 1-3 agenti. Přidej když je to nutné. Méně je víc.

Anti-Pattern 5: Interface Ignorování

Problém: Interface existuje, ale agenti ho ignorují.

Výsledek: Data mismatches, runtime errors.

Jak se vyhnout: TypeScript strict mode. Pokud agent ignoruje interface → build selže. Nutí se dodržovat.

Anti-Pattern 6: Circular Dependencies

Problém: Agent A čeká na B, B čeká na A. Deadlock.

❌ ŠPATNĚ:
FRONTEND: "Čekám na Backend API"
BACKEND: "Čekám na Frontend types"
[Deadlock — nic se nedělá]

✅ SPRÁVNĚ:
ARCHITECT: Definuje interface PRVNÍ
FRONTEND: Chce interface, dostane ji
BACKEND: Chce interface, dostane ji
Oba kódují proti rozhraní, bez čekání

Jak se vyhnout: Interface first. Nikdy circular dependencies. DAG musí být acyclic (bez cyklů).

Checklist: Je Orchestrace Správná?

  • ✅ Všichni agenti mají jasnou roli?
  • ✅ Existuje interface/kontrakt?
  • ✅ Komunikace je přes kód (ne chat)?
  • ✅ DAG je definovaný (bez cyklů)?
  • ✅ Approval mode je Review-Driven?
  • ✅ Rules jsou jasné a vynucované?
  • ✅ Není příliš mnoho agentů?

Pokud všechno OK → Orchestrace je správná!

✓
Shrnutí: Orchestrace Je o Kontrole & Klaritě

TY řídíš. Interface je zákaz. Komunikace je kód. Agenti se řídí. Konflikty jsou řídké a snadné vyřešit. Vše je jasné a traceable.
