MCP servery — co to je a proč to chcete

MCP (Model Context Protocol) je otevřený standard, který umožňuje Claudovi připojit se k externím systémům a nástrojům. Místo toho, abyste kopírovali data z Jiry do chatu, Claude si je přečte sám. Místo ručního volání GitHub API Claude vytvoří PR přímo.

MCP server je malý program (lokální nebo vzdálený), který Claudovi zpřístupňuje sadu nástrojů. Anthropic a komunita poskytují servery pro desítky populárních služeb — a nové přibývají každý týden.

Populární MCP servery

filesystem
Rozšířený přístup k souborům mimo projekt, rekurzivní vyhledávání
github
Issues, PRs, releases, komentáře — vše přes GitHub API
postgres
Přímé SQL dotazy na PostgreSQL databázi
sqlite
Lokální SQLite databáze — bez nutnosti serveru
brave-search
Webové vyhledávání přímo ze session
puppeteer
Ovládání prohlížeče, screenshoty, web scraping
slack
Čtení a posílání zpráv na Slacku
memory
Persistentní paměť mezi sessions (key-value store)
linear
Správa issues, projects a workflows v Linear
jira
Tickety a workflows v Atlassian Jira
notion
Čtení a zápis do Notion dokumentů a databází
docker
Správa kontejnerů, images a volumes

Jak nakonfigurovat MCP server

.claude/settings.json — přidání MCP serverů
{
  "mcpServers": {

    // GitHub — vyžaduje Personal Access Token
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "ghp_váš_token"
      }
    },

    // PostgreSQL — lokální nebo vzdálená DB
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://localhost/myapp_dev"]
    },

    // Brave Search — API klíč z brave.com/search/api
    "brave-search": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-brave-search"],
      "env": {
        "BRAVE_API_KEY": "váš_api_klíč"
      }
    }
  }
}

Po přidání do settings.json restartujte Claude Code. Server se spustí automaticky a Claude bude mít přístup k jeho nástrojům. Ověřte funkčnost příkazem jako: "Jaké jsou otevřené issues v mém GitHub repozitáři?"

Kde najít MCP servery

Oficální seznam: modelcontextprotocol.io/servers. Komunitní servery: GitHub hledání "mcp-server". Claude.ai má připravené vizuální konektory pro Gmail, Google Calendar, Google Drive a Slack — stačí kliknout "Connect" v nastavení.

Hooks — automatizace kolem akcí Clauda

Hooks jsou shell příkazy nebo skripty, které se automaticky spustí před nebo po tom, co Claude provede určitou akci. Umožňují validaci, notifikace, formátování a integraci s externími systémy — bez nutnosti psát to do každého promptu.

Typy hooks a jejich použití

.claude/settings.json — hooks konfigurace
{
  "hooks": {

    // Před zápisem souboru — automatický lint
    "PreToolUse": [
      {
        "matcher": "Write",
        "hooks": [{
          "type": "command",
          "command": "npm run lint --fix"
        }]
      }
    ],

    // Po bash příkazu — notifikace po dlouhém buildu
    "PostToolUse": [
      {
        "matcher": "Bash(npm run build)",
        "hooks": [{
          "type": "command",
          "command": "osascript -e 'display notification \"Build hotov\" with title \"Claude Code\"'"
        }]
      }
    ],

    // Při ukončení session — reminder na commit
    "Stop": [
      {
        "hooks": [{
          "type": "command",
          "command": "git status --short && echo 'Nezapomeňte commitnout!'"
        }]
      }
    ]
  }
}
Praktické use cases pro hooks

Automatický prettier po každém zápisu souboru · Slack notifikace po dokončení agentic tasku · Zápis do logu které soubory Claude změnil · Automatické spuštění testů po každém Write · Upozornění na mobilu když dlouhý build skončí.

Vlastní slash příkazy

Vlastní příkazy jsou Markdown soubory v adresáři .claude/commands/. Jejich název (bez .md) se stane příkazem. Jsou skvělé pro opakující se workflow specifické pro váš projekt — code review podle vašich standardů, release checklist, onboarding skript.

.claude/commands/review.md — příkaz /review
# /review — Code review podle týmových standardů

Proveď code review aktuálních změn oproti main větvi.

Zkontroluj tyto oblasti a pro každý nález uveď:
- Soubor a číslo řádku
- Závažnost: [BLOCKER / WARNING / SUGGESTION]
- Stručný popis problému
- Konkrétní oprava nebo doporučení

**Oblasti kontroly:**
1. Bezpečnost — SQL injection, XSS, odhalení dat, autentizace
2. Výkon — N+1 dotazy, chybějící indexy, velké payloady
3. TypeScript — žádné `any`, správné typy, strict mode
4. Testy — pokrytí edge cases, správné mocking závislostí
5. Konvence — dodržení standardů z CLAUDE.md

Pokud je $ARGUMENTS zadán, reviewuj pouze daný soubor.
Výstup: stručný souhrn + seznam konkrétních problémů.
Použití vlastních příkazů
# Review všech změn
/review

# Review konkrétního souboru ($ARGUMENTS v příkazu)
/review src/auth/login.ts

# Další příklady příkazů k vytvoření:
# /release  — release checklist (build, testy, tag, changelog)
# /onboard  — úvod projektu pro nového vývojáře
# /perf     — analýza výkonu aktuální stránky
# /docs     — aktualizace dokumentace pro změněné funkce

Skills — znalostní moduly pro opakované postupy

Skills jsou strukturované Markdown soubory, které předávají Claudovi specifické technické znalosti nebo step-by-step postupy. Na rozdíl od CLAUDE.md jsou modulární — načtete je jen quando je potřebujete, ne při každé session.

.claude/skills/deploy.md — skill pro nasazení
# Deploy Skill — postup nasazení na produkci

## Předpoklady
Zkontroluj před začátkem:
- [ ] Všechny testy prochází: `npm run test`
- [ ] Build je úspěšný: `npm run build`
- [ ] Není otevřené BLOCKER issue v GitHub

## Postup
1. Vytvoř release tag: `git tag v$(date +%Y.%m.%d) && git push --tags`
2. Počkej na GitHub Actions (typicky 4–6 minut)
3. Zkontroluj Vercel deploy log — hledej ERROR řádky
4. Otestuj produkci na staging.myapp.com/health
5. Zkontroluj Sentry na nové errory (prvních 15 minut)

## Rollback
Pokud deploy selže nebo Sentry ukáže spike errorů:
`vercel rollback` nebo v Vercel Dashboard → Deployments → Revert

Git worktrees — paralelní práce

Git worktrees umožňují mít více větví projektu naklonovaných současně, každou ve vlastním adresáři. Claude Code to využívá pro izolované paralelní sessions — změny v jedné větvi neovlivní ostatní.

Worktrees — základní použití
# Vytvoření worktree pro novou feature
git worktree add ../projekt-feature feature/dark-mode

# Spuštění Claude Code v tomto worktree
cd ../projekt-feature && claude

# Paralelně v dalším terminálu — jiný úkol, jiná větev
git worktree add ../projekt-bugfix hotfix/login-bug
cd ../projekt-bugfix && claude

# Výpis všech aktivních worktrees
git worktree list

# Úklid po mergi
git worktree remove ../projekt-feature
Desktop App + Worktrees = magie

Desktop App (od dubna 2026) vytváří worktrees automaticky pro každou paralelní session. Nemusíte nic ručně konfigurovat — klikněte "New Parallel Session", zadejte úkol a Desktop App zajistí izolaci. Výsledky pak slučujete přes standardní PR review.

Extended Thinking — kdy pomáhá a kdy jen stojí

Extended thinking dává Claudovi prostor "přemýšlet" před odpovědí — interně prochází kroky řešení, zvažuje alternativy a kontroluje svou logiku. Výsledkem je kvalitnější odpověď na složité problémy.

Háček: thinking tokeny se účtují jako output tokeny ($25/MTok na Opus 4.7). Na jednoduchých úkolech to nepřidá žádnou hodnotu — ale stojí vás to 20–50 % extra.

ÚkolThinking potřeba?Doporučení
Návrh systémové architektury✓ Ano/effort high
Debugging záhadného bugu✓ Ano/effort medium
Psaní unit testů✗ Ne/effort low
Přejmenování proměnných✗ Ne/effort low
Code review⚡ Záleží/effort medium
Generování dokumentace✗ Ne/effort low
Ovládání thinking tokenů
## Globální strop v ENV (doporučeno vždy nastavit)
export MAX_THINKING_TOKENS=8000

## V session — přepínání úrovně
/effort low     -- minimum, rychlé odpovědi
/effort medium  -- vyvážené (výchozí)
/effort high    -- maximum — jen pro opravdu těžké úkoly

## Vypnutí pro celou session
/config thinking: false

.claudeignore — co Claude nemá číst

Soubor .claudeignore v kořeni projektu říká Claude Code, které soubory a adresáře má ignorovat při čtení projektu. Funguje stejně jako .gitignore. Klíčové pro bezpečnost (ignorovat .env) a výkon (ignorovat build výstupy).

.claudeignore — doporučená konfigurace
# Citlivé soubory
.env
.env.*
*.pem
*.key

# Build výstupy — zbytečně zvětšují kontext
.next/
dist/
build/
node_modules/

# Logy a dumps
*.log
logs/
dumps/

# Velké datové soubory
*.csv
*.json.bak
fixtures/large/
